## A1. Seeded Data Audit & Health Score Coherence

### Problem

The frontend Dashboard shows a contradiction: every food bank's per-category inventory breakdown shows bars past 100% (supply well exceeding demand per category), yet site health scores are well below 100% and markers show yellow. This confuses the viewer — a site can't simultaneously be overflowing with food and unhealthy.

### Root Cause (Investigate)

The health score formula has four components:

```
health_score = 0.35 × inventory_adequacy
             + 0.25 × category_coverage
             + 0.20 × expiration_risk_inverse
             + 0.20 × demand_fulfillment
```

If inventory adequacy is high (supply > 2 weeks of demand) and category coverage is high (all 6 categories stocked), the only things that could drag health scores down are:

1. **Expiration risk is extreme** — a huge fraction of available inventory expires within 7 days. Check: `SELECT site_id, SUM(quantity_lbs) as expiring FROM inventory WHERE status='available' AND expiration_date < NOW() + interval '7 days' GROUP BY site_id`. If this is most of the inventory, the seeded `expiration_date` values are too aggressive.

2. **Demand fulfillment is low** — the `demand_history` table has `quantity_served_lbs` << `quantity_demanded_lbs`. Check: `SELECT food_category, AVG(quantity_served_lbs / NULLIF(quantity_demanded_lbs, 0)) FROM demand_history GROUP BY food_category`. If the seeded served amounts are much lower than demanded amounts, this drags the score down.

3. **The `compute_health_score` Postgres function has a bug or uses different logic than the spec.** Compare the actual function body against the documented formula. The function may not have been updated when the schema was re-seeded.

4. **The frontend inventory bars are comparing supply to *capacity* (site.capacity_lbs) rather than supply to *demand*.** If a site has 50K lbs capacity and 30K lbs supply, the bar shows 60%. But if weekly demand is only 5K lbs, the site actually has 6 weeks of runway — it's very healthy. The bars need to show the same metric the health score uses (supply vs. demand), not supply vs. physical capacity.

### Required Actions

1. **Run the diagnostic queries above** to identify which health score component is dragging scores down.
2. **Fix the root cause:** If it's seeded data (expiration dates too soon, served amounts too low), fix the seed script. If it's the Postgres function, fix the function. If it's the frontend bar metric, that's a 11B issue — document the correct metric for them.
3. **After fixing, recompute all health scores:** `SELECT compute_health_score(id) FROM sites;` and verify the numbers make sense. A well-stocked site should have health > 0.75. A site with one critical category missing should be 0.5-0.7. An actually struggling site should be < 0.5.

### Constraint

The inventory bar display and the health score marker must tell the same story. If a site shows green bars across all categories, the marker must be green. If a marker is yellow, at least one bar should be yellow/red, or there should be a visible expiration warning.

## A2. Expiration Risk: 0 lbs Over 1M+ lbs

### Problem

The Assessment tab shows "0 lbs expiration risk" despite over a million pounds of total food. Either no inventory rows have expiration dates within 7 days, or the query is broken.

### Investigation

In `gap_analysis.py` lines 60-67:

```python
cutoff = (datetime.now(timezone.utc) + timedelta(days=7)).isoformat()
exp_resp = (
    supabase.table("inventory")
    .select("quantity_lbs")
    .eq("status", "available")
    .lt("expiration_date", cutoff)
    .execute()
)
```

Possible issues:
1. **Seeded expiration dates are all far in the future.** Check: `SELECT MIN(expiration_date), MAX(expiration_date) FROM inventory WHERE status='available'`. If all dates are months out, the seed script needs to include some near-term expirations (especially for produce and dairy — these are the realistic perishables).
2. **Timezone mismatch.** The `cutoff` is UTC, but seeded dates might be naive timestamps that Supabase interprets differently. Check the `expiration_date` column type — if it's `date` (not `timestamptz`), the `.lt()` comparison with an ISO timestamp string may behave unexpectedly.
3. **No data at all.** Some seeded inventory rows may not have `expiration_date` set.

### Required Fix

1. Verify the data. If expiration dates are all distant, update the seed to include realistic perishable items:
   - Produce: 3-7 day expiration from seed date
   - Dairy: 7-14 days
   - Protein (fresh): 3-5 days
   - Canned/grains/beverages: 6-24 months
2. Ensure at least 10-15% of total inventory lbs have expiration within 14 days of the demo date. This makes the expiration risk metric meaningful and gives the health score formula something to work with.
3. Verify the query works after fixing the data. The result should be a non-trivial number (e.g., 15,000-40,000 lbs) that reads as "manageable but worth tracking."

## A3. Optimizer Engine Improvements

### A3.1 Delivery Cost Heuristic (NEW)

Currently, `PlanLineItem` has a `cost` field that only reflects `quantity_lbs × unit_cost_per_lb`. Real food procurement has delivery costs that vary by distance and mode.

**Add to SourceOption model:**

```python
# These fields should be populated by DISCOVER or derived from supplier + site location
latitude: float | None = None
longitude: float | None = None
```

**Delivery cost heuristic:**

```python
import math

def estimate_delivery_cost(
    supplier_lat: float, supplier_lng: float,
    site_lat: float, site_lng: float,
    quantity_lbs: float,
) -> float:
    """
    Estimate delivery cost using haversine distance.
    
    Model: fixed_cost + per_mile_rate × distance + per_lb_rate × weight
    
    Calibrated to approximate Greater Philadelphia logistics:
    - Fixed cost: $75 (truck dispatch, loading)
    - Per mile: $3.50 (fuel, driver time, wear)
    - Per lb: $0.02 (handling, cold chain if applicable)
    
    These numbers are defensible estimates based on USDA 
    food distribution logistics research. The exact values 
    don't matter for the demo — what matters is that distance 
    affects plan cost, making plans meaningfully different.
    """
    # Haversine distance in miles
    R = 3959  # Earth radius in miles
    dlat = math.radians(site_lat - supplier_lat)
    dlng = math.radians(site_lng - supplier_lng)
    a = (math.sin(dlat/2)**2 + 
         math.cos(math.radians(supplier_lat)) * 
         math.cos(math.radians(site_lat)) * 
         math.sin(dlng/2)**2)
    distance_miles = 2 * R * math.asin(math.sqrt(a))
    
    fixed_cost = 75.0
    per_mile = 3.50
    per_lb = 0.02
    
    return round(fixed_cost + per_mile * distance_miles + per_lb * quantity_lbs, 2)
```

**Integration with `_greedy_fill`:** Add `delivery_cost` as a separate field on `PlanLineItem`. The `total_cost` on `ResponsePlan` should be `sum(li.cost + li.delivery_cost for li in line_items)`. This makes the cheapest plan now factor in proximity — a $0/lb donated source 50 miles away costs more to deliver than a $0.50/lb source 5 miles away.

**Update PlanLineItem model:**

```python
class PlanLineItem(BaseModel):
    # ... existing fields ...
    delivery_cost: float = 0.0  # NEW
    distance_miles: float = 0.0  # NEW — useful for map visualization
```

### A3.2 Food Bank → Food Bank Transfers (NEW)

This is a novel feature that demonstrates network-level thinking. If Site A has surplus protein and Site B has a protein deficit, CrisisGrid should suggest a transfer rather than ordering new supply.

**Concept:** After computing per-site gap analysis, identify sites where `supply > demand × 1.5` (significant surplus) in categories where other sites have deficits. Generate transfer suggestions as a special type of line item.

**Implementation approach (context for planner — solve this during planning):**

The planner needs to decide where this logic lives. Options:

1. **Inside `generate_plans()` as a pre-processing step:** Before running greedy fill against external sources, run a transfer matching algorithm that pairs surplus sites with deficit sites. Transfer items get added to line_items with `supplier_name = "Transfer: [Source Site Name]"`, `unit_cost_per_lb = 0.0`, and delivery cost based on inter-site distance. Remaining deficits after transfers go to external sources.

2. **As a separate step after plan generation:** Run transfer analysis on the gap data, produce a `transfers: list[TransferItem]` alongside `line_items` on each plan. This keeps the optimizer clean but requires a new model.

**Key considerations:**
- Transfers only make sense within the same plan. A site shouldn't be told to transfer food it needs for its own demand.
- The surplus threshold matters. Don't suggest transferring food from a site that's at exactly 100% coverage — only from sites with clear excess.
- Transfer cost is delivery-only (no procurement cost), which makes them very attractive in the cheapest plan.
- The fastest plan should only include transfers between nearby sites (< 15 miles).
- Transfers need a distinct visual treatment in the Map tab (Spec 11B handles the UI — this spec handles the data model and logic).

**New model:**

```python
class TransferItem(BaseModel):
    from_site_id: str
    from_site_name: str
    to_site_id: str
    to_site_name: str
    food_category: str
    quantity_lbs: float
    delivery_cost: float
    distance_miles: float
```

**Add to ResponsePlan:**

```python
class ResponsePlan(BaseModel):
    # ... existing fields ...
    transfers: list[TransferItem] = []  # NEW
```

### A3.3 Strategy Differentiation Resilience

The Phase 10 fix (filter fastest to ≤2-day sources) works for current data but may break with different datasets. Make the strategies more resilient:

**Fastest:**
- Primary: sources where `lead_time_days <= 2`
- Fallback 1: sources where `lead_time_days <= 3`
- Fallback 2: top 50% of sources by lead time (sort ascending, take first half)
- Always: transfers between nearby sites (< 15 miles) included as "immediate" options

**Cheapest:**
- Sort all sources by `unit_cost_per_lb + estimated_delivery_cost_per_lb`
- The delivery cost inclusion is what makes this strategy genuinely different — a free donated source far away may cost more delivered than a cheap local source
- Transfers are very attractive here (procurement cost = $0)

**Best Nutrition:**
- Round-robin across categories (existing logic is correct)
- But add a diversity penalty: if a category already has ≥ 80% coverage, deprioritize it in favor of uncovered categories
- This prevents the round-robin from over-filling one category when others are still empty

### A3.4 Response Plan Description Accuracy

The `strategy` string on each plan needs to accurately describe what the algorithm actually does. After implementing the above changes, update the strategy descriptions to match. The frontend displays these directly, so they need to be both accurate and human-readable.

Example:
- **Not:** "Minimize delivery time" (vague)
- **Better:** "Fastest delivery: only sources that can arrive within 2 days, plus nearby inter-site transfers"

## A4. Plan Acceptance → Database → Dashboard

### Concept

When a user selects a plan in the Plans tab, it should:
1. Write the accepted plan to the `crisis_events` table (the `response_plan` jsonb column)
2. Simulate the effect on inventory (add incoming quantities, subtract transfers)
3. Recompute health scores for affected sites
4. Emit SSE events so the frontend can update the Dashboard metrics live

This is the "close the loop" moment in the demo — the director selects a plan and immediately sees the network health improve.

### Implementation

**New endpoint:** `POST /api/plans/accept`

```python
@router.post("/api/plans/accept")

    """
    Accept a response plan. Writes to crisis_events, updates 
    projected inventory, recomputes health scores.
    """

    supabase.table("crisis_events").update({
        "response_plan": req.plan.model_dump(),
        "status": "active",
        "health_score_projected_after": projected_score,
    }).eq("id", req.crisis_event_id).execute()
    
    # 2. For each line item, INSERT into inventory with status='reserved'

    for item in req.plan.line_items:
        supabase.table("inventory").insert({
            "site_id": req.target_site_id,  # which site receives this
            "food_category": item.food_category,
            "quantity_lbs": item.quantity_lbs,

            "expiration_date": estimate_expiration(item.food_category),
```

- How should transfers affect the source site's inventory? Subtract immediately (showing the cost of the transfer) or mark as `reserved_for_transfer`?

## A5. Order Sheet Generation

### Concept

Once a plan is accepted, generate downloadable documents that a food bank director could actually send to suppliers. This demonstrates that CrisisGrid doesn't just analyze — it produces actionable output.

### Documents to Generate

**1. Purchase Order (per supplier):**
For each supplier in the accepted plan's line items, generate a PO with:
- Supplier name, address, contact
- Line items: item name, quantity, unit cost, total cost
- Delivery requirement (lead time from plan)
- Requesting organization info
- PO number (auto-generated)
- Format: PDF or markdown (for demo, markdown rendered in a modal is fine; PDF is stretch)

**2. Transfer Request (per inter-site transfer):**
For each transfer in the plan:
- Source site name and address
- Destination site name and address
- Items to transfer: category, quantity
- Suggested logistics (distance, estimated delivery cost)
- Authorization line for both site directors

**3. Crisis Response Summary:**
Single document consolidating:
- Crisis profile (type, geography, severity, timeline, affected population)
- Gap analysis summary (total deficit, per-category breakdown)
- Selected plan name and strategy
- All line items and transfers
- Total cost breakdown (procurement + delivery)
- Expected coverage improvement
- AI cost (from Lava) — "This analysis cost $X.XX in AI compute"
- Timestamps for every pipeline stage

### Implementation

**New endpoint:** `GET /api/plans/{crisis_event_id}/documents`

Returns a list of document objects, each with:
```python
class GeneratedDocument(BaseModel):
    type: str  # "purchase_order" | "transfer_request" | "crisis_summary"
    title: str
    supplier_name: str | None  # for POs
    content_markdown: str  # renderable content
    # Stretch: content_pdf_url: str
```

The frontend (Spec 11B) will display these in a "Documents" section or modal. The content generation is template-based (no LLM needed) — fill in the values from the accepted plan data.

## A6. Auditability — Provenance for Every Agent Call

### Problem

In a live demo, a judge might ask "how do I know this is real?" Every claim in the Assessment tab, every source found in DISCOVER, and every plan generated should be traceable to specific API calls with timestamps and model identifiers.

### Implementation

**1. Pipeline event log:**

Every SSE event already has a timestamp. What's missing is a persistent audit trail. During pipeline execution, append to a `pipeline_audit_log` list:

```python
@dataclass
class AuditEntry:
    timestamp: float
    agent: str           # "scope", "assess", "discover", "optimize", "monitor"
    action: str          # "llm_call", "tool_call", "supabase_query", "hex_trigger"
    model: str | None    # "claude-sonnet-4-20250514" or None for non-LLM
    input_summary: str   # truncated prompt or query
    output_summary: str  # truncated response or result count
    token_count: int | None
    cost_usd: float | None
    lava_request_id: str | None  # for linking to Lava dashboard
```

**2. Store with crisis event:**

After pipeline completes, serialize the audit log and store it in the `crisis_events` row alongside `crisis_profile`, `gap_analysis`, and `response_plan`:

```sql

```

**3. Expose via API:**

`GET /api/crisis/{event_id}/audit` returns the full audit log. The frontend can render this as an expandable timeline with links to Lava for cost verification.

**4. Per-call model identification:**

The SSE events for agent steps should include which model was called. This is already partially there in `orchestrator_step` events. Extend to all LLM-backed agents:

## A7. Plans Hex Notebook — Creation & Integration

### What This Is

A Hex project (`CrisisGrid-Plans`) that takes the three generated response plans as input and produces a visual comparison dashboard. This is embedded in the Plans tab as an iframe alongside the plan cards.

### Input Parameters

Single input parameter: `plan_data_json` (text) — a JSON string containing all three plans.

### Notebook Structure

1. **Python cell:** Parse `plan_data_json` into DataFrames
2. **Chart: Plan Comparison** — grouped bar chart with three clusters (Fastest / Cheapest / Best Nutrition), each showing cost, coverage %, and lead time
3. **Chart: Sourcing Breakdown** — stacked bar showing each plan's source composition by supplier type (donated, purchased, USDA, transfer)
4. **Chart: Category Coverage by Plan** — radar or grouped bars showing per-category coverage for each plan
5. **Chart: Cost Breakdown** — procurement cost vs. delivery cost for each plan
6. **Table: Line Item Detail** — full table of all line items across plans, sortable and filterable

### Integration

The backend triggers this Hex project after `generate_plans()` completes:

```python
# In the pipeline, after optimize completes:
plan_data = [p.model_dump() for p in plans]
hex_run = await trigger_hex_run(
    HEX_PLANS_PROJECT_ID,
    {"plan_data_json": json.dumps(plan_data)}
)
emit_event(SSEEvent(type="hex_run_started", hex_url=hex_run.run_url, hex_project="plans"))
```

The frontend receives the `hex_run_started` event for the plans project and embeds the iframe in the Plans tab.

### Hex Project Setup

1. Create project in Hex
2. Add Supabase data connection (same as ASSESS notebook)
3. Add input parameter `plan_data_json` (text type)
4. Build cells as described above
5. Publish, set sharing to "Anyone with link"
6. Set `HEX_PLANS_PROJECT_ID` in `.env`
7. Pre-run once and cache the `runUrl` as fallback

### Sync Requirement

The plan data sent to Hex must exactly match what the Plans tab cards display. Both come from the same `generate_plans()` output. The SSE event `plans_ready` already contains the plan data — the Hex trigger should use the same data. No separate computation.

## A8. Crisis Report Storage

### Problem

After a full pipeline run, all the outputs (crisis profile, gap analysis, plans, audit log, order sheets) need to be stored together as a coherent "crisis report" that can be retrieved later.

### Implementation

The `crisis_events` table already has jsonb columns for `crisis_profile`, `gap_analysis`, and `response_plan`. Extend it:

```sql
ALTER TABLE crisis_events 
  ADD COLUMN IF NOT EXISTS discovered_sources jsonb,
  ADD COLUMN IF NOT EXISTS all_plans jsonb,       -- all 3 plans, not just accepted
  ADD COLUMN IF NOT EXISTS accepted_plan_name text,
  ADD COLUMN IF NOT EXISTS audit_log jsonb,
  ADD COLUMN IF NOT EXISTS hex_assess_url text,
  ADD COLUMN IF NOT EXISTS hex_plans_url text,
  ADD COLUMN IF NOT EXISTS pipeline_duration_ms integer,
  ADD COLUMN IF NOT EXISTS total_ai_cost_usd float8;
```

**Write at pipeline completion:**

```python
# After pipeline finishes, before returning
supabase.table("crisis_events").update({
    "crisis_profile": profile.model_dump(),
    "gap_analysis": gap.model_dump(),
    "discovered_sources": [s.model_dump() for s in sources],
    "all_plans": [p.model_dump() for p in plans],
    "audit_log": [entry.__dict__ for entry in audit_log],
    "hex_assess_url": assess_run_url,
    "hex_plans_url": plans_run_url,
    "pipeline_duration_ms": duration,
    "total_ai_cost_usd": total_cost,
}).eq("id", crisis_event_id).execute()
```

This makes the full crisis report queryable and retrievable. The Follow-up tab (Hex Threads) can then answer questions like "what was the total cost of our last crisis response?" by querying this table.
